## 2. Project summary

A CRM-style application where AI agents read customer emails and calendars from the Microsoft 365 ecosystem to:

1. **Track customers** through the lifecycle, keeping current stage, engagement history, and next action up to date.
2. **Schedule meetings**: when a customer offers times by email, check internal team availability, propose common slots, and on approval create the Outlook/Teams meeting and record it in the CRM.

One-line description: a CRM that reads the inbox, understands where each customer stands, suggests the next action, and books the meeting.

Platform direction:

- Primary: Microsoft Graph, Microsoft Agent Framework with Azure OpenAI (GPT) models, Microsoft 365 Agents Toolkit (Teams), Azure AI Foundry.
- Fallback (Phase 1, the working system): synthetic `.eml` emails, mock calendar JSON, local model via Ollama.

## 4. Scope

In scope:

- Email ingestion, customer matching, stage classification, summaries, next actions.
- Scheduling from customer-offered times, including conflicts, no-overlap counter-proposals, clarification requests, and rescheduling an existing meeting.
- CRM API, web dashboard, human approval flow, audit trail.
- Teams Copilot agent (see open decision D6 for timing).

Out of scope:

- Reading the external customer's own calendar (they are outside the organization; their availability comes only from their emails).
- Autonomous sending or booking without approval.
- Channels other than email.
- Replacing an enterprise CRM product.

## 5. Lifecycle stages

Fixed enumeration in the domain model. Each CRM store adapter maps it to its own representation.

| Stage                  | Definition                                                                                            |
| ---------------------- | ----------------------------------------------------------------------------------------------------- |
| Initial Lead           | First contact; no established two-way conversation yet.                                               |
| Engagement             | Active two-way conversation, discovery, or arranging an intro/discovery call.                         |
| Presentation/Follow-up | Demo, walkthrough, or proposal delivered, or a presentation meeting is confirmed; includes follow-up. |
| Converted              | Customer has committed (signed order form, purchase approval).                                        |
| Not Converted          | Customer declined, chose another vendor, or closed; capture the reason when stated.                   |

Every stage change is recorded in a stage history (previous stage, new stage, timestamp, reason, source email).

## 6. Architecture

```
UI:        Web Dashboard, Teams Copilot Agent
              |  (both call the same API)
Backend:   CRM API -> Agent Orchestrator -> agents:
              Ingestion, Stage Classifier, Summary and Next Action,
              Scheduler, CRM Writer
Providers: MailProvider, CalendarProvider, ChatModelProvider, CrmRepository
Live:      Microsoft Graph, Exchange Online, Azure OpenAI (Foundry), Entra ID
Local:     Synthetic EML files, Mock Calendar JSON, Ollama
Data:      CRM Store, Audit and Trace Store
Observability: App Insights (live) / structured logs (local)
External client: communicates by email only
```

Principle: every external dependency is behind a provider interface chosen by configuration. Agents depend on interfaces only.

### Provider interfaces (language-neutral; adapt to the chosen language)

```
MailProvider
  list_new_messages(since)            -> [Email]
  get_message(id)                     -> Email
  create_reply_draft(thread, body)    -> DraftRef
  send_draft(draft_ref)               -> void        # only after approval

CalendarProvider
  get_availability(users, start, end) -> per user: {working_hours, busy_blocks: [{start, end, showAs}]}
  create_event(event)                 -> EventRef    # online meeting if live
  update_event(event_key, changes)    -> EventRef    # reschedule / add attendee
  find_event(event_key)               -> Event | None
  find_events(users, attendee_addresses, start, end) -> [Event]   # events with attendees and event key; used to locate an existing meeting for a reschedule

ChatModelProvider
  complete(messages, output_schema)   -> validated structured result
                                          # validate against schema; retry on malformed output

CrmRepository
  customers, contacts, emails, engagements, meetings,
  stage_history, next_actions, scheduling_requests, audit entries
  + named queries: customers_by_stage, stale_leads(days),
    next_actions_due(range), customer_timeline(customer_id)
```

Implementations:

| Interface         | Live (written, unverified in Phase 1)                | Local (working in Phase 1)                                                                    |
| ----------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| MailProvider      | Microsoft Graph                                      | Reads `.eml` files, replays in date order against the simulated clock                         |
| CalendarProvider  | Microsoft Graph                                      | Reads mock calendar JSON; also records meetings the system creates so later bookings see them |
| ChatModelProvider | Azure OpenAI via Microsoft Agent Framework / Foundry | Ollama                                                                                        |
| CrmRepository     | Azure SQL or Dataverse (undecided)                   | SQLite                                                                                        |

Configuration selects the implementation per provider. Optional: health-check fallback from live to local. Record the active provider for each call in the audit log.

## 7. Functional requirements

### Ingestion (Ingestion Agent)

- `FR-ING-1` Normalize every email (live or `.eml`) into one internal `Email` object.
- `FR-ING-2` Strip quoted earlier messages; analyze only the new text.
- `FR-ING-3` Match an email to a customer using sender address, sender domain, CC contacts, and thread identifiers (Message-ID, In-Reply-To, References, conversation ID). New subject lines for an existing customer must still link by domain/contacts.
- `FR-ING-4` Create a new lead when no customer matches.
- `FR-ING-5` Ignore exact duplicates (same Message-ID) without creating a second record.
- `FR-ING-6` Ignore unrelated internal mail (for example all-staff announcements) and create no CRM record.
- `FR-ING-7` Process both received and sent (Sent Items) emails; both update engagement history.
- `FR-ING-8` Add newly seen contacts (for example CC'd colleagues) to the customer.
- `FR-ING-9` Store attachment names/metadata with the email.

### Stage classification (Stage Classifier Agent)

- `FR-CLS-1` Input: new email text plus current stage, running summary, and recent engagement entries, bounded to fit the model's context window.
- `FR-CLS-2` Output a schema-validated result: proposed stage, confidence, short reason, extracted facts (for example user count, current CRM, decision timeline, loss reason).
- `FR-CLS-3` Do not change stage on an unanswered follow-up nudge or on historical dates mentioned in old emails.
- `FR-CLS-4` Record the stage change and reason in stage history.

### Summary and next action

- `FR-SUM-1` Update a running engagement summary after each email.
- `FR-SUM-2` Propose a next action (description, optional due date). Examples: send deck, schedule intro call, answer questions, onboarding kickoff, re-engage in April.

### Scheduling (Scheduler Agent)

- `FR-SCH-1` Detect scheduling intent in an email.
- `FR-SCH-2` Extract the customer's offered windows into structured slots with explicit time zone, resolving relative dates ("next Thursday") and converting to UTC. Do not trigger scheduling from historical times in old emails. Resolve relative dates against the email's sent date in the sender's time zone. Use the simulated clock only to discard times already in the past. Determine the sender's time zone from the contact's stored zone; otherwise from an explicit zone in the email text; otherwise from candidates implied by the Date header offset plus hints in the text, validated in code. If still ambiguous, ask the customer to confirm instead of guessing.
- `FR-SCH-3` If the request is vague (no concrete times), or the sender's time zone is still ambiguous after the FR-SCH-2 steps, draft a clarification request. The scheduling request's outcome is request_clarification. Create no meeting.
- `FR-SCH-4` Select internal attendees from assignment rules (`config/team.json`), and add relevant CC'd customer contacts as external attendees.
- `FR-SCH-5` Read availability via `CalendarProvider`; apply blocking rules from section 8.
- `FR-SCH-6` Compute the overlap in code. Cap open-ended customer windows by internal working hours. Rank results and return at most 3 suggestions.
- `FR-SCH-7` Outcomes, exactly one of: `recommend_slots`, `counter_propose` (no overlap), `request_clarification`, `update_existing_meeting`.
- `FR-SCH-8` For `counter_propose`, draft a reply with 2 or 3 mutual slots in the customer's time zone, within the customer's stated preferences (for example mornings). Create no meeting.
- `FR-SCH-9` For a reschedule request, locate the existing meeting using find_events: upcoming, non-cancelled events on the assigned attendees' calendars that include an external attendee address from the trigger email (falling back to the sender's domain). If exactly one matches, update it and add any new attendee. If several match, narrow by the original meeting day mentioned in the email. Otherwise draft a clarification request and create nothing. Never create a duplicate meeting.
- `FR-SCH-10` A team member not assigned to the meeting must never block it.
- `FR-SCH-11` Include a human-readable reason for every accepted and rejected slot in the scheduling request record.
- `FR-SCH-12` A scheduling request has a state: pending, approved, rejected, superseded, cancelled, expired, or needs_review.

### Approval

- `FR-APP-1` Present proposed slot(s), attendees, and the draft reply for approve, edit draft text, or reject. Editing changes only the draft text.
- `FR-APP-2` Only after approval: create or update the event, create the confirmation reply as a mailbox draft, and send it.
- `FR-APP-3` Record the approval decision, who made it, and when.
- `FR-APP-4` At approval, re-check availability for the chosen slot. If a conflict appeared, do not book; mark needs_review with fresh options. After a conflict, approval progress returns to not_started. The approver then approves one of the fresh options or rejects.
- `FR-APP-5` Approval runs as recorded, idempotent, retryable steps. A failure leaves the approval partially_completed with the failed step visible.

### CRM Writer

- `FR-CRM-1` Persist all outcomes through `CrmRepository` only: stage changes, engagement entries, meetings, contacts, next actions, scheduling requests.
- `FR-CRM-2` Meeting record includes event key, subject, UTC start/end, attendees, join link (marked simulated in local mode), status, customer response status.

### API and UI

- `FR-API-1` One CRM API serves both UI surfaces and exposes customers, timelines, next actions, scheduling requests, approvals, and a trigger for the agent workflow.
- `FR-UI-1` Dashboard pipeline view: customers grouped by stage.
- `FR-UI-2` Customer detail: stage, contacts, engagement timeline (emails and meetings), next action.
- `FR-UI-3` Scheduling panel: parsed customer windows, availability results with reasons, proposed slots, draft reply, approve/edit/reject.
- `FR-UI-4` Audit view: what each agent decided, with provider and model used.
- `FR-UI-5` Teams Copilot agent offers conversational access to the same API ("where does Fabrikam stand?", "what are my next actions this week?").

### Audit and configuration

- `FR-AUD-1` Record every agent run: agent, input reference, output, provider and model, timestamp, duration, approval decision.
- `FR-CFG-1` Provider selection and all settings come from configuration. See `example.env` keys in section 14.

## 9. Data model (store-neutral)

Define these in the application's own domain model. CRM store adapters (SQLite, Azure SQL, Dataverse) map them.

- **Customer**: id, company name, email domain, stage (enumeration), account owner, created date, loss reason.
- **Contact**: id, customer id, name, email, role/title, time zone (if known).
- **EmailMessage**: Message-ID, thread identifiers, direction (received/sent), sender, to, cc, sent time and zone, subject, new body (quoted text removed), attachment names.
- **Engagement**: id, customer id, type (email, meeting, note), summary, timestamp, source reference.
- **Meeting**: id, customer id, event key (iCalUId), subject, start/end UTC, attendees (internal and external), join link (simulated flag), status, customer response status.
- **StageHistory**: customer id, previous stage, new stage, timestamp, reason, source (an email, or an approval).
- **NextAction**: customer id, description, due date, status.
- **SchedulingRequest**: customer id, trigger email, parsed customer slots, attendees considered, evaluated results with reasons, proposed slots, outcome type, draft reply, state (pending, approved, rejected, superseded, cancelled, expired, needs_review), decision (approve or reject), decided_by, decided_at, approval progress (not_started, in_progress, completed, partially_completed). Each approval step's result is recorded as an AgentRun audit entry linked to the request. Editing a request changes only the draft text and is recorded as an audit entry; it does not change the state. Also: fresh options (replace the proposed slots after a re-check conflict; the earlier slots are kept in an audit entry), state reason, and superseded_by (id of the newer request).
- **AgentRun**: agent, input reference, output, provider, model, timestamp, duration, approval decision.

## 11. Local mode details

- **Mail**: replay `.eml` files in date order against the simulated clock so the system behaves as if mail arrives one message at a time. Parse headers (Message-ID, In-Reply-To, References, Date with offset, From/To/Cc), multipart bodies, and attachments.
- **Calendar**: read the mock calendar JSON (Graph event shape; `showAs` values `free|tentative|busy|oof|workingElsewhere`). Persist meetings created by the system so later availability checks see them. Graph-like event shape (attendees as plain address strings; no isCancelled, so a missing value means not cancelled)
- **Model (Ollama)**: small local models are weaker at structured output. Validate every output against a schema and retry on malformed output. Keep scheduling logic in code (`R4`). Record stage-classification accuracy against the answer key so the user can judge whether the local model is good enough. Model choice is open decision D5.
- **CRM store**: SQLite behind `CrmRepository`.
- **Simulated values**: mark simulated join links and similar values explicitly (`R10`).
